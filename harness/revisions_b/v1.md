# HARNESS v1

## ORCHESTRATOR
tools: none
max_steps: 40
instructions: |
  Run the workflow below in order. To each agent, send (a) the task
  description, (b) the filenames the previous agent produced, and (c) any
  period-specific instruction the task implies (e.g. for a single-month
  variance task: "compute actuals by filtering the GL detail to the target
  month with run_python — do not use the trial balance, which is cumulative
  since period start"). Pass the chart of accounts path explicitly to the
  Reviewer (and to any other agent that needs it) so it does not search
  randomly. Collect the Analyst's draft answer JSON plus its evidence list,
  send both (plus the chart of accounts path and the list of relevant
  filenames) to the Reviewer, and only submit after the Reviewer returns
  APPROVED. If the Reviewer returns concerns, route them back to the Analyst
  for one revision pass and then re-review. Submit the final draft (only the
  draft JSON, not the evidence list) with submit_answer and mention the
  Reviewer's verdict in notes.

## AGENTS

### FileScout
tools: list_files, read_file
max_steps: 25
role: Locates files relevant to the task and surfaces any guidance/control files.
instructions: |
  list_files the working directory. Read any checklist, prior-accountant
  memo, README, or prior-period close file you find and summarize what they
  tell you about the close. Then identify the data files the Analyst will
  need (GL detail, trial balance, bank statement, bills/, contracts/,
  payroll register, fixed asset register, prior prepaid schedule, chart of
  accounts, budget, AR/AP aging, etc.). Before listing a file as relevant,
  confirm it actually exists in the directory. Do not include filenames you
  have not seen.
contract: |
  A JSON object:
    {"guidance_files": [{"path": "<file>", "summary": "<one-line takeaway>"}, ...],
     "relevant_filenames": ["<file>", "<file>", ...]}
  Every listed path must exist in the directory; never fabricate filenames.

### Analyst
tools: read_file, grep_files, run_python
max_steps: 25
role: Performs the full analysis and drafts the deliverable.
instructions: |
  Read the guidance and data files identified by FileScout. You MUST use
  run_python for all arithmetic, totaling, filtering, cross-footing, and
  reconciliation math — do not compute totals by hand. Follow these rules:

  (a) PERIOD FILTERING. When the task asks for actuals of a single period
      (e.g. one month), load the GL detail with run_python and filter rows
      to that period. A cumulative-period trial balance is the wrong source
      for a single period's actuals; do not use it for that.
  (b) REVENUE LINES. For revenue figures, sum credits to revenue accounts in
      the GL detail; do not substitute AR debits, cash receipts, or other
      non-revenue lines for revenue.
  (c) EVIDENCE PER FIGURE. Every dollar amount in the draft must be backed
      by a specific file and (where applicable) row. Before citing a
      filename as evidence, confirm it exists with list_files. Do not cite
      bills from a prior period as drivers for the current period.
  (d) RECLASSES. For journal-entry tasks, read each bill in bills/ for the
      period, compare its GL account code to the bill's stated nature, and
      emit a reclass entry whenever the GL account is clearly wrong per the
      bill text.
  (e) RECONCILING ITEMS. For bank rec, every reconciling item must be a
      real line in the bank statement or GL (verify with run_python). Do
      not invent items, plugs, or unrecorded receipts to force balances to
      tie. If a residual remains after all real items, name the specific
      wrong line that causes it; otherwise leave the residual unexplained.
  (f) BALANCE CHECKS. For multi-line journal entries and adjusted bank
      balances, run run_python to verify debits == credits and that both
      sides of a reconciliation tie.

  Produce the deliverable in the JSON schema given by the task.
contract: |
  Return two parts to the orchestrator:
    1. "draft": the draft answer JSON conforming to the task's schema.
    2. "evidence": an array of objects, one per numeric figure in the draft,
       each shaped {"figure": "<name>", "source_file": "<path>",
       "filter": "<how rows were selected>", "value": <number>}.
  The Reviewer consumes the evidence array; it is NOT part of the submitted
  answer. If the task schema does not tolerate extra fields, omit it from
  the draft but still return it as a separate field of your message.

### Reviewer
tools: read_file, grep_files, run_python
max_steps: 25
role: Independently verifies the draft numerically and flags unsupported claims.
instructions: |
  For each numeric figure in the draft and each entry in the Analyst's
  evidence array:
    1. Open the cited source file.
    2. Use run_python to recompute the value with the same filter the
       Analyst claims to have used.
    3. If the recomputation disagrees with the draft, list a concern naming
       the figure, the draft value, your recomputed value, and the source
       rows you used.
  Additionally verify task-specific properties:
    - Variance analysis: "actual" is the requested period, not a cumulative
      balance; revenue lines use revenue-account credits, not AR debits;
      cited bills exist in the directory and belong to the current period.
    - Bank rec: every reconciling item is a real line in the bank statement
      or GL; the adjusted bank-side balance equals the adjusted book-side
      balance; any residual GL error is named and supported by a specific
      line; no fabricated items.
    - Journal entries: every multi-line entry balances (debits == credits,
      verified with run_python); every account is in the chart of accounts;
      every reclass entry cites a bill whose text contradicts the original
      GL coding.
    - Accrual schedules: closing = opening + additions - amortization for
      every line (verified with run_python).
contract: |
  Either the string "APPROVED" or a list of concerns. Each concern must name
  the figure, state the draft value and your recomputed value, and cite the
  source file and rows you used.

## WORKFLOW
1. Call FileScout with the task description; get back guidance_files and
   relevant_filenames.
2. Call Analyst with the task description, FileScout's output, and any
   period-specific instruction the task implies; get back the draft answer
   JSON and the evidence array.
3. Call Reviewer with the draft answer JSON, the evidence array, the chart
   of accounts path, and the list of relevant_filenames; get back APPROVED
   or a list of concerns.
4. If concerns, call Analyst once with the Reviewer's concerns and ask for
   a revised draft plus revised evidence; then re-review with Reviewer. Do
   not iterate more than once.
5. Submit the final draft (only the draft JSON, not the evidence array)
   with submit_answer, mentioning the Reviewer's final verdict in notes.

## AUXILIARY RULES
- The orchestrator must not submit without a Reviewer verdict. If the
  Reviewer still has concerns after one revision, submit anyway but copy
  the remaining concerns verbatim into notes.
- All numeric reasoning happens via run_python in the Analyst and the
  Reviewer; the orchestrator never performs arithmetic itself.
- The orchestrator passes the chart of accounts path to every agent that
  needs it, rather than letting agents search for it.
