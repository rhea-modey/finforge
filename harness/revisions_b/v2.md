# HARNESS v2

## ORCHESTRATOR
tools: none
max_steps: 40
instructions: |
  Run the workflow below in order. Send each agent one message describing the
  task and what you need back from it. When forwarding between agents, include
  the original task description verbatim plus any prior agent's output so
  downstream agents have full context. Collect the Analyst's draft answer
  JSON, show it to the Reviewer, then submit the draft with submit_answer.

## AGENTS

### FileScout
tools: list_files, read_file
max_steps: 25
role: Locates the files relevant to the task.
instructions: |
  List the files in the working directory. Read the close checklist, the prior
  accountant memo, and any task description file in full, then skim the
  remaining files. Group filenames by purpose (checklist/memo, source ledgers,
  contracts, bills, schedules, budgets, statements) and list any files that
  look unrelated so the Analyst can confirm they are not needed.
contract: |
  A grouped list of relevant filenames with a one-line purpose tag for each
  group, plus any out-of-scope filenames you noticed.

### Analyst
tools: list_files, read_file, grep_files, run_python
max_steps: 25
role: Performs the full analysis and drafts the deliverable.
instructions: |
  Read the relevant files identified by FileScout and complete the entire
  task yourself. Produce the deliverable exactly in the JSON schema given in
  the task description. Follow this procedure:

  1. Read every relevant file in full. Always read the close checklist, the
     prior accountant memo, the chart of accounts, the prior-period schedule
     (if any), the GL/ledger export, the bank statement, the trial balance,
     and every bill or contract the checklist references. Do not skim.
  2. Before drafting any deliverable, build a checklist-to-entry map: for
     every numbered or named checklist item, state the source file, the
     computed amount, the exact debit account (number AND name from
     chart_of_accounts.csv), the exact credit account, and the status
     (already_booked with the cited GL line, to_book, or not_required).
  3. Use `run_python` to compute every numeric total in your draft (account
     balances, variances, reconciling subtotals, schedule roll-forwards,
     adjusted balance). Print the intermediate subtotals in the trace so the
     orchestrator can audit them; do not rely on mental arithmetic.
  4. For bank reconciliation, `reconciling_items` is a FLAT array of objects
     with the exact field names specified in the task description (e.g.
     kind, side, ref, date, amount). Do not nest items under book_side or
     bank_side objects and do not rename top-level keys.
  5. For journal entries, every debit and credit must use an account number
     that appears in chart_of_accounts.csv. Combine multi-line prepaid
     amortization into a single entry when the task requests it. Cross-foot
     each entry (debits = credits) with `run_python`.
  6. For variance analysis, compute figures on the AS-CLOSED basis: apply
     every required close entry (accruals, amortization, depreciation,
     reclasses of miscoded bills) from the checklist before comparing to
     budget. Each driver must name a SPECIFIC vendor, invoice number, bill
     ID, payroll period, or document — never a generic "expense incurred in
     period" or a single ledger citation. The drivers for one account must
     sum to that account's reported variance.

contract: |
  The draft answer JSON whose keys, types, and nesting exactly match the
  schema in the task description. In the message body (not the JSON),
  include the checklist-to-entry map: every checklist item, its source file,
  its computed amount, its accounts, and its status.

### Reviewer
tools: list_files, read_file, grep_files, run_python
max_steps: 25
role: Independently verifies the draft answer against source files.
instructions: |
  You will be given the task description, the draft answer JSON, and the
  Analyst's checklist-to-entry map. Do NOT trust the draft without
  independent verification. Specifically:

  1. Schema check: confirm every required key from the task description is
     present with the correct type and nesting. Reject renamed, restructured,
     or wrapped keys (for example, `reconciling_items` nested under a
     book_side/bank_side object instead of a flat array).
  2. Cross-foot check: pick at least two numeric totals from the draft and
     recompute them with `run_python` against the source files. Report the
     recomputed value alongside the draft's value in your reply.
  3. Checklist coverage: confirm every checklist item has a corresponding
     entry or section. For `to_book` entries, confirm the amount and
     accounts. For `already_booked` entries, confirm the cited GL line.
  4. Account validity: for every journal entry, confirm the account numbers
     exist in chart_of_accounts.csv. Flag any account that does not.
  5. Driver specificity: for variance drivers, confirm each names a specific
     vendor, invoice, bill ID, or payroll period — not a generic citation.
  6. No fabrication: confirm no journal entry references an account that
     does not exist, and that no entry duplicates or reverses a balanced
     posting incorrectly.

contract: |
  Either "APPROVED" with a one-sentence justification naming the specific
  totals independently recomputed and their values, OR a numbered list of
  concrete failures each citing the field, the source file, and the
  expected vs. actual value. APPROVED requires evidence of independent
  recomputation; APPROVED without it is treated as NOT APPROVED.

## WORKFLOW
1. Call FileScout with the task description; get back the grouped filename
   list and the out-of-scope notes.
2. Call Analyst with the task description, the grouped filename list, and an
   explicit reference to the six-step procedure; get back the draft answer
   JSON plus the checklist-to-entry map.
3. Call Reviewer with the task description, the draft JSON, and the
   checklist-to-entry map; get back APPROVED-with-evidence or a numbered
   list of concrete failures.
4. If the Reviewer returned failures, call Analyst once more with the
   failures and the original context, requesting a revised draft and
   re-review. Retry at most once; if still failing, submit the most accurate
   draft available.
5. Submit the final draft answer JSON with submit_answer, mentioning the
   Reviewer's verdict and any remaining concerns in notes.

## AUXILIARY RULES
- All numeric totals in the Analyst's draft MUST be produced by a `run_python`
  script whose intermediate subtotals are printed in the conversation trace.
  The orchestrator will not accept totals that the Analyst asserts without a
  corresponding script output.
- The Analyst MUST read chart_of_accounts.csv before proposing any journal
  entry and use only account numbers that appear in it. The orchestrator
  will reject journal entries referencing account numbers not in the chart.
- For bank reconciliation, `reconciling_items` MUST be a flat array of
  objects; nesting it inside book_side/bank_side objects is a schema
  violation and grounds for rejection.
- For variance analysis, each driver MUST name a specific vendor, invoice,
  bill ID, payroll period, or document. Generic "expense incurred in period"
  drivers are rejected.
- Variance analysis MUST be computed on the AS-CLOSED basis: apply every
  required close entry (accruals, amortization, depreciation, reclasses of
  miscoded bills) from the close checklist before comparing actuals to
  budget. Submitting raw GL totals as "actuals" is grounds for rejection.
- The Reviewer MUST independently recompute at least two numeric totals with
  `run_python` before returning APPROVED. APPROVED without recomputation
  evidence is treated as NOT APPROVED.
