# HARNESS v1

## ORCHESTRATOR
tools: none
max_steps: 50
instructions: |
  Run the workflow below in order. For every agent call, pass: (a) the full task
  description, (b) the categorized file manifest from FileScout, and (c) any
  prior agent output the next agent needs verbatim. After the Calculator reports,
  if there are CONCERNS with corrected figures, send the Analyst ONE revision pass
  containing the Calculator's issue list and corrected numbers, then re-run the
  Calculator. Do not bypass the Calculator's verdict when submitting.

## AGENTS

### FileScout
tools: list_files, read_file
max_steps: 20
role: Discovers and categorizes source files relevant to the close task.
instructions: |
  Use list_files to inventory the working directory. Skim the first ~30 lines of
  any file whose name suggests relevance to the task category (bank rec, journal
  entries, variance analysis, accrual/prepaid schedules, fixed assets, payroll,
  notes/checklists). Group what you find by purpose: trial balance, bank
  statement, GL detail, payroll register, budget, fixed asset register,
  prepaid/accrual schedules, bills/invoices/source documents, notes/checklists,
  chart of accounts, schema or sample files.
contract: |
  A categorized manifest: a JSON object whose keys are purpose categories and
  whose values are lists of {path, one_line_note} entries. Include any
  chart-of-accounts and schema/sample files under their own keys.

### Analyst
tools: read_file, grep_files, run_python
max_steps: 30
role: Performs the close-period analysis and drafts the deliverable JSON.
instructions: |
  Read every file the manifest lists. Before drafting, ENUMERATE the full set of
  items the task requires and decide the status of each (booked / needs_entry /
  not_applicable), with a one-line justification. Do not silently drop items.

  Apply these task-specific conventions (do not improvise):
  - Bank reconciliation: build a two-column workpaper. "Bank-side" items adjust
    the BANK balance (outstanding checks, deposits in transit, bank errors).
    "Book-side" items adjust the BOOK balance (bank fees, interest, items on the
    statement not yet in the GL, GL errors). Both columns must tie to the SAME
    adjusted balance. Outstanding checks and deposits in transit require NO
    journal entry (they are already in the books).
  - Variance analysis: drivers must sum to the VARIANCE for that account, not
    to the actual. If the task calls for an as-closed basis, post the standard
    close entries (payroll accrual, prepaid amortization, depreciation,
    reclasses) BEFORE computing period actuals.
  - Prepaid/accrual schedules: produce a roll-forward row for EVERY prepaid or
    accrued account identified on the trial balance / prior schedule; do not
    omit items just because their numbers are small.
  - Journal entries: each entry's lines must sum debits = credits; do not
    propose entries for items already posted in the GL (verify with a grep).
    If a checklist item requires no entry, say so explicitly.

  For ALL arithmetic (totals, footings, reconciliations, divisions, amortization,
  driver sums, schedule roll-forwards), use run_python -- do not compute in your
  head. For every figure you assert, record the run_python expression that
  produced it so the Calculator can reproduce it.

  Produce the deliverable in EXACTLY the JSON schema the task specifies.
contract: |
  Two parts, both required:
  (1) "draft": the answer JSON matching the task schema.
  (2) "working_notes": a JSON object listing (a) every checklist item with
      status (booked/needs_entry/not_applicable) and one-line justification;
      (b) every arithmetic step as {claim, expression, result, source_file};
      (c) for bank recs, the bank-side column, book-side column, and computed
      adjusted balance; (d) for variances, actual/budget/variance per account
      and the source documents supporting each driver; (e) for schedules, the
      roll-forward arithmetic per row.

### Calculator
tools: run_python, read_file
max_steps: 25
role: Independently verifies all arithmetic and tie-outs in the Analyst's draft.
instructions: |
  Open the source files the Analyst cites. With run_python, recompute every
  arithmetic claim in working_notes from the raw file data and run these
  specific checks (do not redo the analysis, only verify and correct):

  - Bank rec: bank_balance + bank-side adjustments must equal book_balance +
    book-side adjustments, and both must equal the submitted adjusted_balance.
    Identify bank-side vs book-side by comparing the bank statement against
    the GL cash postings; outstanding checks and deposits in transit are
    bank-side, bank fees/interest are book-side.
  - Journal entries: for every entry, sum(lines.debit) must equal
    sum(lines.credit).
  - Variance: for each reported account, recompute actual - budget from the
    GL and budget files; for each driver set, sum(driver.amount) must equal
    the variance (not the actual) within $0.01.
  - Schedule roll-forwards: opening + additions - amortization = closing per
    row; the journal entry tied to the schedule must balance.
  - Completeness: the GL/trial-balance count of items in each category
    (prepaid accounts, reconciling items, accounts with material variance,
    checklist entries) must match what the draft covers.

  For each failed check, compute the corrected figure from raw data.
contract: |
  A verdict object. If every check passes within $0.01:
    {"verdict": "APPROVED", "checks_run": [...names...]}
  Otherwise:
    {"verdict": "CONCERNS", "issues": [{"check": "...", "expected": ...,
    "found": ..., "corrected": ..., "evidence": "..."}, ...], "checks_run":
    [...names...]}. The "corrected" value MUST be the figure recomputed from
    raw data via run_python, not a guess. If a tie-out cannot be made to
    reconcile to within $0.01 even after recomputation, say so in the issue.

### Reviewer
tools: read_file
max_steps: 12
role: Confirms schema compliance and that Calculator-flagged issues are addressed.
instructions: |
  Read the Analyst's final draft, the Calculator's verdict, and at least two
  source files the Analyst cites (verify the paths exist by listing or
  reading). Confirm: (a) the draft JSON matches the task schema -- correct
  field names, types, dates in YYYY-MM-DD, allowed enum values; (b) every
  issue the Calculator flagged is either fixed in the draft (with the
  Calculator's corrected figure) or honestly noted as a known unresolved
  discrepancy; (c) the cited source files actually exist and contain the
  data the draft claims. Do NOT re-run arithmetic -- the Calculator owns that.
contract: |
  APPROVED, or a short list of remaining concerns the Calculator missed
  (schema violations, missing fixes, cited files that do not exist). Empty
  list of concerns means APPROVED.

## WORKFLOW
1. Call FileScout with the task description; receive the categorized file manifest.
2. Call Analyst with the task description, the manifest, and the conventions
   from the Analyst's instructions; receive {draft, working_notes}.
3. Call Calculator with the draft, the working_notes, and the manifest;
   receive the verdict.
4. If the verdict is CONCERNS, call Analyst once with the issue list and
   corrected figures, asking it to revise; then call Calculator again.
   Repeat at most twice total.
5. Call Reviewer with the final draft, the Calculator's final verdict, and
   the manifest; receive APPROVED or remaining concerns.
6. Submit the Analyst's final draft JSON with submit_answer. If the Reviewer
   raised concerns or the Calculator never reached APPROVED, note the
   unresolved items in the submission.

## AUXILIARY RULES
- Acceptance gate: Calculator must return APPROVED before submission. If after
  two revision passes the Calculator still reports CONCERNS on a tie-out,
  submit the Analyst's latest draft only with a note describing the unresolved
  discrepancy; do not silently override the Calculator's corrected figures.
- The Analyst is forbidden from asserting any figure that is not backed by a
  run_python expression in working_notes. The Calculator must reject any
  claim it cannot reproduce from the cited source data within $0.01.
- If a task's checklist contains items the data does not require (e.g., no
  reclasses needed), the Analyst must state "not_applicable" for that item
  with a one-line justification rather than omitting it silently. The
  Reviewer must flag any silent omissions.
