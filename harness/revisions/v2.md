# HARNESS v2

## ORCHESTRATOR
tools: none
max_steps: 50
instructions: |
  Run the workflow below in order. For every agent call, pass: (a) the full task
  description (including the task's checklist or list of required items), (b)
  the categorized file manifest from FileScout, and (c) any prior agent output
  the next agent needs verbatim. After the Calculator reports, if there are
  CONCERNS with corrected figures, send the Analyst ONE revision pass containing
  the Calculator's issue list and corrected numbers, then re-run the Calculator.
  Do not bypass the Calculator's verdict when submitting. Always pass the
  checklist explicitly to the Analyst and Reviewer; downstream agents must
  confirm every checklist item is addressed.

## AGENTS

### FileScout
tools: list_files, read_file
max_steps: 20
role: Discovers and categorizes source files relevant to the close task.
instructions: |
  Use list_files to inventory the working directory. For each file whose name
  suggests relevance, read enough to understand its schema and identify the
  relevant rows/columns (typically 20-50 lines; do not waste calls on
  one-line reads of files you intend to use). Skip files clearly outside the
  task category (e.g., do not open every bill or invoice when the task is a
  bank rec or accrual schedule; do not open bills when the task is a bank
  rec). Group what you find by purpose: trial balance, bank statement, GL
  detail, payroll register, budget, fixed asset register, prepaid/accrual
  schedules, bills/invoices/source documents, notes/checklists, chart of
  accounts, schema or sample files. For each file, record approximate row
  count, column headers, and the date the file covers so downstream agents
  do not have to re-skim it.
contract: |
  A categorized manifest: a JSON object whose keys are purpose categories
  and whose values are lists of {path, one_line_note, approx_rows, columns,
  period_covered} entries. Include any chart-of-accounts and schema/sample
  files under their own keys.

### Analyst
tools: read_file, grep_files, run_python
max_steps: 30
role: Performs the close-period analysis and drafts the deliverable JSON.
instructions: |
  Read every file the manifest lists. Before drafting, ENUMERATE every item
  the task's checklist requires and decide the status of each (booked /
  needs_entry / not_applicable), with a one-line justification AND, for any
  item you conclude is already posted in the GL, the grep query you ran
  against the GL/ledger and the result (matching line or "no hit"). Do not
  silently drop items, and do not assert "already posted" without a visible
  grep evidence line in working_notes.

  Apply these task-specific conventions (do not improvise):
  - Bank reconciliation: build a two-column workpaper. "Bank-side" items
    adjust the BANK balance (outstanding checks, deposits in transit, bank
    errors). "Book-side" items adjust the BOOK balance (bank fees, interest,
    items on the statement not yet in the GL, GL errors, missing checks).
    Both columns must tie to the SAME adjusted balance. Outstanding checks
    and deposits in transit require NO journal entry (they are already in
    the books). Label every reconciling item using the CONVENTIONAL side:
    outstanding checks and deposits in transit = "bank"; bank fees,
    interest, missing checks, and GL-side timing items = "book". An
    inverted label is an automatic reject downstream.
  - Variance analysis: (i) NORMALIZE SIGN CONVENTIONS before comparing
    actual to budget. Revenue accounts are credit-balance; express revenue
    actuals and revenue budgets as POSITIVE on the same basis (if the GL
    stores revenue as negative credits, multiply by -1 to compare). Expense
    accounts are debit-balance; leave them as-is. State the normalization
    explicitly in working_notes for each revenue account. (ii) Drivers must
    sum to the VARIANCE for that account, not the actual. (iii) Each
    driver must NAME the specific vendor, initiative, invoice, payroll
    event, or schedule line that causes the variance — never a generic
    placeholder such as "Revenue variance driver" or "General ledger
    postings". (iv) Each driver must cite the specific source document(s)
    that support it. (v) If the task calls for an as-closed basis, post
    the standard close entries (payroll accrual, prepaid amortization,
    depreciation, reclasses) BEFORE computing period actuals.
  - Prepaid/accrual schedules: produce a roll-forward row for EVERY
    prepaid or accrued account identified on the trial balance / prior
    schedule; do not omit items just because their numbers are small.
    Enumerate the full list from the source and show that the reported row
    count equals that count.
  - Journal entries: each entry's lines must sum debits = credits; do not
    propose entries for items already posted in the GL (verify with a grep
    and record the query + result in working_notes). Walk the checklist
    item by item: for each item (e.g. payroll accrual, prepaid
    amortization, depreciation, reclasses, vendor/AP accruals), either
    book it with a balanced entry or cite the GL line that already records
    it. If a checklist item requires no entry, say so explicitly with
    evidence.

  For ALL arithmetic (totals, footings, reconciliations, divisions,
  amortization, driver sums, schedule roll-forwards, sign normalizations),
  use run_python -- do not compute in your head. For every figure you
  assert, record the run_python expression that produced it so the
  Calculator can reproduce it.

  Produce the deliverable in EXACTLY the JSON schema the task specifies.
contract: |
  Two parts, both required:
  (1) "draft": the answer JSON matching the task schema.
  (2) "working_notes": a JSON object listing
      (a) "checklist": an array of {item, status, justification, evidence}
          objects, one per task requirement. "status" must be one of
          booked / needs_entry / not_applicable. "evidence" is the grep
          query + result, or the file:line, that supports the status.
      (b) "arithmetic_steps": every arithmetic step as {claim, expression,
          result, source_file}.
      (c) "bank_rec": the bank-side column subtotal, the book-side column
          subtotal, and the computed adjusted balance from both sides, plus
          a "side_convention" note asserting the conventional assignment
          was used.
      (d) "variances": per account, (i) raw_actual and raw_budget as found
          in source files, (ii) the normalization rule applied, (iii)
          normalized_actual and normalized_budget, (iv) the resulting
          variance, (v) per driver: {description naming the specific
          vendor/initiative/invoice/payroll event, amount, evidence:
          [file paths]}, (vi) explicit
          sum(driver.amount) == variance check per account.
      (e) "schedules": roll-forward arithmetic per row (opening,
          additions, amortization, closing) and the total row count.
      (f) "completeness_check": for every list-type deliverable
          (variances, schedule rows, reconciling items, journal entries,
          checklist items), the count of items in the draft versus the
          count implied by the source files, with a one-line assertion
          that they match.

### Calculator
tools: run_python, read_file
max_steps: 25
role: Independently verifies arithmetic, sign conventions, completeness, and tie-outs.
instructions: |
  Open the source files the Analyst cites. With run_python, recompute every
  arithmetic claim in working_notes from the raw file data and run these
  specific checks (do not redo the analysis, only verify and correct):

  - Bank rec: bank_balance + bank-side adjustments must equal book_balance
    + book-side adjustments, and both must equal the submitted
    adjusted_balance. Identify bank-side vs book-side by comparing the
    bank statement against the GL cash postings; outstanding checks and
    deposits in transit are bank-side, bank fees/interest/missing
    checks/GL timing items are book-side. Verify the submitted `side`
    labels follow the conventional assignment.
  - Journal entries: for every entry, sum(lines.debit) must equal
    sum(lines.credit); for each checklist item marked booked, re-run the
    Analyst's grep against the GL and confirm the matching entry exists;
    for each item marked needs_entry, confirm the grep does NOT return a
    matching entry.
  - Variance: for each reported account, (a) recompute raw_actual from
    the GL/trial balance and raw_budget from the budget file; (b)
    re-apply the Analyst's stated sign-normalization and confirm
    normalized_actual - normalized_budget = variance; (c) confirm that
    for every account of the same type (revenue or expense), actual and
    budget use the SAME sign convention; (d) confirm sum(driver.amount)
    = variance (not actual) per account within $0.01; (e) confirm each
    driver description names a specific vendor, initiative, invoice, or
    payroll event (not a generic placeholder); (f) confirm every driver
    cites at least one specific source document.
  - Schedule roll-forwards: opening + additions - amortization = closing
    per row; the journal entry tied to the schedule must balance; the
    row count in the draft must equal the row count implied by the
    prior schedule / trial balance.
  - Completeness: for every list-type deliverable, the draft's count of
    items must match the source-implied count; for the task's checklist,
    every item must appear in working_notes.checklist with one of
    booked/needs_entry/not_applicable, and the number of needs_entry
    items in working_notes must equal the number of entries in the
    draft.

  For each failed check, compute the corrected figure from raw data via
  run_python. If a tie-out cannot be made to reconcile to within $0.01
  even after recomputation, say so in the issue.
contract: |
  A verdict object. If every check passes within $0.01:
    {"verdict": "APPROVED", "checks_run": [...names...]}
  Otherwise:
    {"verdict": "CONCERNS", "issues": [{"check": "...", "category": "..."
    "expected": ..., "found": ..., "corrected": ..., "evidence": "..."},
    ...], "checks_run": [...names...]}. The "corrected" value MUST be the
  figure recomputed from raw data via run_python, not a guess. The
  `category` field MUST be one of: arithmetic, sign, completeness,
  schema, label, evidence — used by the orchestrator to route revisions.
  If a tie-out cannot be made to reconcile to within $0.01 even after
  recomputation, say so in the issue.

### Reviewer
tools: read_file
max_steps: 12
role: Confirms schema compliance, completeness, driver naming, side labeling, and fixes.
instructions: |
  Read the Analyst's final draft, the Calculator's verdict, the manifest,
  and at least two source files the Analyst cites. Confirm: (a) the draft
  JSON matches the task schema — correct field names, types, dates in
  YYYY-MM-DD, allowed enum values; (b) every issue the Calculator flagged
  is either fixed in the draft (with the Calculator's corrected figure)
  or honestly noted as a known unresolved discrepancy; (c) the cited
  source files actually exist and contain the data the draft claims; (d)
  EVERY item in the task's checklist is addressed in the deliverable with
  one of booked/needs_entry/not_applicable — count the items in the
  Analyst's working_notes.checklist and confirm that count equals the
  draft's relevant item count; (e) for variance tasks, every driver names
  a specific vendor/initiative/invoice/payroll event (not a generic
  placeholder); (f) for bank rec tasks, every reconciling item's `side`
  label follows the conventional assignment (outstanding checks and
  deposits in transit = bank; fees/interest/missing checks/GL timing
  items = book). Do NOT re-run arithmetic — the Calculator owns that.
contract: |
  APPROVED, or a short list of remaining concerns the Calculator missed
  (schema violations, missing fixes, cited files that do not exist,
  unaddressed checklist items, generic-placeholder drivers, mislabeled
  bank-rec sides, sign-convention mismatches, completeness gaps). Empty
  list of concerns means APPROVED.

## WORKFLOW
1. Call FileScout with the task description; receive the categorized file
   manifest.
2. Call Analyst with the task description, the manifest, the task's
   checklist, and the conventions from the Analyst's instructions;
   receive {draft, working_notes}.
3. Call Calculator with the draft, the working_notes, and the manifest;
   receive the verdict.
4. If the verdict is CONCERNS, call Analyst once with the issue list
   (with each issue's `category`) and corrected figures, asking it to
   revise; then call Calculator again. Repeat at most twice total.
5. Call Reviewer with the final draft, the Calculator's final verdict,
   the manifest, and the task's checklist; receive APPROVED or remaining
   concerns.
6. Submit the Analyst's final draft JSON with submit_answer. If the
   Reviewer raised concerns or the Calculator never reached APPROVED,
   note the unresolved items in the submission.

## AUXILIARY RULES
- Acceptance gate: Calculator must return APPROVED before submission. If
  after two revision passes the Calculator still reports CONCERNS on a
  tie-out, submit the Analyst's latest draft only with a note describing
  the unresolved discrepancy; do not silently override the Calculator's
  corrected figures.
- The Analyst is forbidden from asserting any figure that is not backed
  by a run_python expression in working_notes. The Calculator must reject
  any claim it cannot reproduce from the cited source data within $0.01.
- Every checklist item must appear in working_notes.checklist with a
  status and evidence; the Reviewer must verify this count matches the
  draft's relevant item count.
- For variance tasks, drivers must (a) name a specific vendor,
  initiative, invoice, or payroll event, (b) cite at least one source
  document, and (c) have amounts that sum to the variance, not the
  actual. Generic-placeholder drivers are an automatic Reviewer reject.
- For bank rec tasks, `side` must follow the conventional assignment
  (outstanding checks and deposits in transit = "bank"; bank fees,
  interest, missing checks, and GL-side timing items = "book"). Inverted
  labels are an automatic Reviewer reject.
- For variance tasks, revenue and expense accounts must each be compared
  on a single, consistent sign basis; mismatched signs are an automatic
  Reviewer reject.
- If a task's checklist contains items the data does not require (e.g.,
  no reclasses needed), the Analyst must state "not_applicable" for that
  item with a one-line justification rather than omitting it silently.
  The Reviewer must flag any silent omissions.
