# HARNESS v3

## ORCHESTRATOR
tools: none
max_steps: 30
instructions: |
  Run the workflow below STRICTLY in the listed order; do not improvise extra
  passes. For every agent call, pass: (a) the full task description, (b) the
  categorized file manifest from FileScout (reuse it for all later calls; do
  NOT re-spawn FileScout), and (c) any prior agent output the next agent needs
  verbatim. Do not call any single agent more than the maximum number of times
  specified in WORKFLOW. ALWAYS end the run by calling submit_answer with the
  final Analyst draft and a notes string; if the draft is incomplete, submit
  the incomplete draft rather than nothing. Do not bypass the Calculator's
  verdict when submitting.

## AGENTS

### FileScout
tools: list_files, read_file
max_steps: 20
role: Discovers and categorizes source files relevant to the close task.
instructions: |
  Use list_files to inventory the working directory. Skim the first ~30 lines of
  any file whose name suggests relevance to the task category (bank rec, journal
  entries, variance analysis, accrual/prepaid schedules, fixed assets, payroll,
  notes/checklists). Group what you find by purpose: trial balance, bank
  statement, GL detail, payroll register, budget, fixed asset register,
  prepaid/accrual schedules, bills/invoices/source documents, notes/checklists,
  chart of accounts, schema or sample files. Read any close-checklist or notes
  file IN FULL if present; include its full text (or a structured item-by-item
  list of required tasks) under the "checklist" key so downstream agents see
  every required item without re-reading it.
contract: |
  A categorized manifest: a JSON object whose keys are purpose categories and
  whose values are lists of {path, one_line_note} entries. Include any
  chart-of-accounts and schema/sample files under their own keys. Under the
  "checklist" key, include the full text of the close-checklist or a
  structured item-by-item list of required tasks.

### Analyst
tools: read_file, grep_files, run_python
max_steps: 30
role: Performs the close-period analysis and drafts the deliverable JSON.
instructions: |
  Read every file the manifest lists. Read the close-checklist in full from
  the manifest before drafting. BEFORE drafting the deliverable, build a
  `checklist_status` object that maps every required checklist item to its
  status and evidence; populate the deliverable only after this map is
  complete.

  Apply these task-specific conventions (do not improvise):
  - Bank reconciliation: build a two-column workpaper. "Bank-side" items
    adjust the BANK balance (outstanding checks, deposits in transit, bank
    errors). "Book-side" items adjust the BOOK balance (bank fees, interest,
    items on the statement not yet in the GL, GL errors). Both columns must
    tie to the SAME adjusted balance using ONLY real reconciling items found
    in the source documents; if the two sides do not tie, search the bank
    statement and GL for additional reconciling items (duplicate postings,
    misposted amounts, bank errors, deposits the bank has not yet credited)
    until they do; NEVER introduce a fictitious, "plug", "balancing", or
    "reconciliation adjustment" item to force a tie. Outstanding checks and
    deposits in transit require NO journal entry (they are already in the
    books).
  - Variance analysis: drivers must sum to the VARIANCE for that account, not
    to the actual; each driver must be a POSITIVE amount representing an
    incremental CAUSE of the variance (never the budget itself, never a
    back-solved plug, never a negative amount). If a residual gap remains
    after listing every driver you can identify, add a final driver labeled
    "Unexplained residual" with the residual amount rather than scaling
    other drivers. If the task calls for an as-closed basis, book the
    standard close entries (payroll accrual, prepaid amortization,
    depreciation, reclasses) BEFORE computing period actuals; the actuals
    must reflect the post-close P&L. Confirm the period basis of the budget
    (monthly vs cumulative) and use actuals over the SAME period; state the
    period basis in the evidence for each variance.
  - Prepaid/accrual schedules: produce a roll-forward row for EVERY prepaid
    or accrued account identified on the trial balance / prior schedule / GL
    (also grep the GL for postings to the relevant asset and expense
    accounts; do not omit items just because the prior schedule did not list
    them). The opening balance for each row must tie LINE BY LINE to the
    prior-period schedule or the prior-period trial balance; if the
    prior-period figure does not match, show the discrepancy. An
    "already_booked" status must cite the specific GL line (date, account,
    amount) that already records the amortization; otherwise the status is
    "to_book".
  - Journal entries: each entry's lines must sum debits = credits; do not
    propose entries for items already posted in the GL (verify with a grep
    for the amount, account, and date). Mark a checklist item
    "not_applicable" only with POSITIVE evidence that the underlying
    transaction does not exist for the period OR that a GL line already
    records the same entry; absence of a GL line is evidence the entry IS
    needed, not that it is not_applicable.

  For ALL arithmetic (totals, footings, reconciliations, divisions,
  amortization, driver sums, schedule roll-forwards), use run_python -- do
  not compute in your head. For every figure you assert, record the
  run_python expression that produced it so the Calculator can reproduce it.

  Produce the deliverable in EXACTLY the JSON schema the task specifies.
contract: |
  Three parts, all required:
  (1) "draft": the answer JSON matching the task schema.
  (2) "working_notes": a JSON object listing (a) every checklist item with
      status (booked / already_booked / needs_entry / not_applicable) and
      one-line justification citing specific evidence; (b) every arithmetic
      step as {claim, expression, result, source_file}; (c) for bank recs,
      the bank-side column, book-side column, and computed adjusted balance,
      with every item traced to a specific bank statement or GL line; (d)
      for variances, actual/budget/variance per account, the period basis
      used, and the source documents supporting each driver; (e) for
      schedules, the roll-forward arithmetic per row including the
      opening-to-prior-period tie-out.
  (3) "checklist_status": a JSON object whose keys are the literal checklist
      item identifiers from the task description or close-checklist file
      (use the exact text the source uses), and whose values are
      {"status": "booked"|"already_booked"|"needs_entry"|"not_applicable",
       "deliverable_ref": "<path into the draft JSON where this item is
       reflected, or 'N/A'>",
       "evidence": "<one-line source pointer: a specific GL line with date
       and amount, a specific schedule row, or a specific source file>"}.
      Every required item from the checklist must appear; "not_applicable"
      and "already_booked" statuses must cite specific evidence -- generic
      statements like "not needed", "already handled", "no GL line exists"
      are NOT acceptable evidence.

### Calculator
tools: run_python, read_file
max_steps: 25
role: Independently verifies all arithmetic and tie-outs in the Analyst's draft.
instructions: |
  Open the source files the Analyst cites. With run_python, recompute every
  arithmetic claim in working_notes from the raw file data and run these
  specific checks (do not redo the analysis, only verify and correct):

  - Bank rec: bank_balance + bank-side adjustments must equal book_balance +
    book-side adjustments, and both must equal the submitted adjusted_balance.
    Identify bank-side vs book-side by comparing the bank statement against
    the GL cash postings; outstanding checks and deposits in transit are
    bank-side, bank fees/interest are book-side. Every reconciling item must
    trace to a specific bank statement line or GL line; flag any item that
    does not (suspected plug).
  - Journal entries: for every entry, sum(lines.debit) must equal
    sum(lines.credit).
  - Variance: for each reported account, recompute actual - budget from the
    GL and budget files; for each driver set, sum(driver.amount) must equal
    the variance (not the actual) within $0.01; every driver must have a
    positive amount and a source evidence pointer; flag any driver that is
    the budget itself, that does not trace to a source document, or that has
    a negative amount.
  - Schedule roll-forwards: opening + additions - amortization = closing per
    row; the opening must equal the prior-period schedule row or
    prior-period trial balance line; the journal entry tied to the schedule
    must balance.
  - Completeness: every item in the Analyst's checklist_status must appear;
    every "not_applicable" or "already_booked" status must cite specific
    evidence; flag any item without evidence or any missing item.

  For each failed check, compute the corrected figure from raw data.
contract: |
  A verdict object. If every check passes within $0.01:
    {"verdict": "APPROVED", "checks_run": [...names...]}
  Otherwise:
    {"verdict": "CONCERNS", "issues": [{"check": "...", "expected": ...,
    "found": ..., "corrected": ..., "evidence": "..."}, ...], "checks_run":
    [...names...]}. The "corrected" value MUST be the figure recomputed from
    raw data via run_python, not a guess. If a tie-out cannot be made to
    reconcile to within $0.01 even after recomputation, say so in the issue.

### Reviewer
tools: read_file
max_steps: 12
role: Confirms schema compliance and checklist completeness.
instructions: |
  Read the Analyst's final draft, the Calculator's final verdict, the
  Analyst's checklist_status, and at least two source files the Analyst
  cites (verify the paths exist by listing or reading). Confirm: (a) the
  draft JSON matches the task schema -- correct field names, types, dates
  in YYYY-MM-DD, allowed enum values; (b) every issue the Calculator
  flagged is either fixed in the draft (with the Calculator's corrected
  figure) or honestly noted as a known unresolved discrepancy; (c) the
  cited source files actually exist and contain the data the draft claims;
  (d) EVERY item in the Analyst's checklist_status is either reflected in
  deliverable_ref OR has specific evidence supporting its status -- flag
  any item with status "not_applicable" or "already_booked" that lacks a
  specific GL/schedule pointer; (e) no required checklist item is missing
  from the checklist_status map. Do NOT re-run arithmetic -- the
  Calculator owns that. The orchestrator will invoke you exactly once; do
  not expect a re-call.
contract: |
  APPROVED, or a short list of remaining concerns the Calculator missed
  (schema violations, missing checklist items, items lacking evidence, cited
  files that do not exist). Empty list of concerns means APPROVED.

## WORKFLOW
1. Call FileScout ONCE with the task description; receive the categorized
   file manifest (including the close-checklist text or item list under the
   "checklist" key). Reuse this manifest for all later calls.
2. Call Analyst ONCE with the task description and the manifest; receive
   {draft, working_notes, checklist_status}.
3. Call Calculator ONCE with the draft, the working_notes, the
   checklist_status, and the manifest; receive the verdict.
4. If the Calculator verdict is CONCERNS, call Analyst ONCE with the issue
   list and corrected figures, asking it to revise {draft, working_notes,
   checklist_status}; then call Calculator ONCE again. Do not revise more
   than once.
5. Call Reviewer ONCE with the final draft, the Calculator's final verdict,
   the checklist_status, and the manifest; receive APPROVED or remaining
   concerns. Do not re-call Reviewer.
6. ALWAYS call submit_answer with the Analyst's final draft JSON. In the
   notes field, summarize: which checklist items are reflected in the draft,
   which items are missing or unresolved, and any known discrepancies.
   Never let the run terminate without submit_answer.

## AUXILIARY RULES
- Acceptance gate: Calculator must return APPROVED before submission when
  feasible. If after the single revision pass the Calculator still reports
  CONCERNS on a tie-out, submit the Analyst's latest draft with a notes
  string describing the unresolved discrepancy and the Calculator's
  corrected figures; do not silently override the Calculator's corrected
  figures, and do not skip submit_answer.
- The Analyst is forbidden from asserting any figure that is not backed by
  a run_python expression in working_notes. The Calculator must reject any
  claim it cannot reproduce from the cited source data within $0.01.
- The Analyst must mark a checklist item "not_applicable" or
  "already_booked" only with specific evidence (a GL line with date and
  amount, a schedule row, or a named source document); generic statements
  like "not needed", "already handled", or "no GL line exists" are NOT
  acceptable evidence, and the Reviewer must flag them.
- If a task's checklist contains items the data does not require, the
  Analyst must still enumerate every checklist item in checklist_status
  with status and evidence; silent omission is not permitted. The Reviewer
  must flag any item missing from checklist_status.
- The orchestrator must invoke each agent at most the number of times
  listed in WORKFLOW. Re-invoking FileScout, Reviewer, or any other agent
  beyond the stated maximum is a workflow violation. The orchestrator must
  always end the run with a submit_answer call, even if the draft is
  partial or the Calculator raised unresolved concerns.
